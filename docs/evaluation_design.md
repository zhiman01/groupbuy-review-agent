# 评测体系设计：分层指标与驱动迭代机制

> 本文档展示团购复盘诊断 Agent 的评测体系设计方法论，可直接用于面试演示。

---

## 一、为什么分三层指标

Workflow 和 Agent 要测的东西不一样：

| 类型 | 测什么 | 为什么分开 |
|------|--------|-----------|
| **Workflow** | 单次输入→输出对不对 | 路径固定，测"结果质量" |
| **Agent** | 多轮对话中的决策质量 | 路径开放，测"过程质量" |

所以指标分三层：**红线指标 → 质量指标 → Agent 增量指标**，逐层过滤。

---

## 二、红线指标（命中即判失败，不进质量分）

**业务上不可接受的错**，一条都不能有。

| 编号 | 指标 | 判定标准 | 业务后果 |
|------|------|---------|---------|
| **R1** | 合规越权 | 直接下达"立即降价/马上下架"强制指令，或未标注"需确认"就给调价下架结论 | 一条越权指令 = 业务不可用 |
| **R2** | 幻觉编造 | 编造 group_deals 里没有的优惠/活动，或不存在的商家数据 | 商家信任崩塌 |

**设计逻辑：** 红线指标是"一票否决"，不是加权扣分。因为合规和真实性是底线，不是"可以妥协的质量维度"。

---

## 三、质量指标（红线过了才打）

**反映诊断质量高低**，用 1-5 分打分。

| 编号 | 指标 | 评分标准 | 权重 |
|------|------|---------|------|
| **Q1** | 归因准确 | 四类根因（流量/转化/商品/品控）是否符合业务事实 | 30% |
| **Q2** | 信息缺口声明 | 信息不足时是否声明"需验证什么"而非硬归因 | 25% |
| **Q3** | 报告完整度 | 三段式（核心问题/建议方向/需确认）是否齐 | 20% |
| **Q4** | 双输出区分 | 内部分析 vs 商家话术是否恰当分开、对外话术是否合规 | 25% |

**Q2 是核心亮点：** 这个指标直接对应"不幻觉"的克制能力。普通 Agent 会硬编结论，我们的 Agent 会声明"需验证套餐改动记录、退款订单原因、商圈竞品曝光量"。

---

## 四、Agent 增量指标（Workflow 没有的过程维度）

**测多轮对话中的决策质量**，只有 Agent 场景才有。

| 编号 | 指标 | 评分标准 | 典型失败 case |
|------|------|---------|--------------|
| **A1** | 工具调用合理性 | 该调 workflow 时调、该轻答时别硬跑全量 | 用户问"你好"，Agent 硬跑完整 workflow |
| **A2** | 主动追问恰当性 | 该问时问、不该问时不啰嗦 | 信息够了还追问，或信息不够不追问 |
| **A3** | 多轮上下文跟随 | 记住约束（如"不降价"） | 用户说"不降价"，下一轮 Agent 又建议降价 |

---

## 五、关键设计：每个指标都能定位到"该改哪一层"

**这张表是评测驱动迭代的核心机制**——指标不达标，直接指到病根在哪一层：

| 不达标的指标 | 定位到哪一层 | 怎么改 | 真实案例 |
|-------------|-------------|--------|---------|
| **R1 合规越权** | 护栏层 | 词表/审查规则 | V1→V2 迭代：固定词表→强制信号词 |
| **R2 幻觉** | Prompt 的 grounding 约束 / 上游数据 | 加"只引用真实字段"或补数据 | 早期测试发现 Agent 编造不存在的优惠 |
| **Q1 归因不准** | 根因诊断节点 prompt / 上游数据 | 改诊断 prompt 或查数据是否误导 | 发现"服务品控"维度归因过于笼统 |
| **Q2 硬归因** | 人设"信息不足先声明"规则 | 强化该规则 | 早期 Agent 在信息不足时硬编结论 |
| **A1 工具乱调** | Agent 人设调用规则 / workflow 描述 | 明确调用条件 | 用户问"你好"，Agent 硬跑 workflow |
| **A3 多轮丢失** | 对话历史配置 | 打开 chatHistory | **今天真实遇到过**：会话上下文配置问题 |

**这张表的价值：** 普通人列一堆指标就完了；你能说清"每个指标坏了对应哪一层的病"，这才是评测驱动迭代的机制。

---

## 六、闭环：从评测到迭代的完整链路

```
构造对抗集（按失败模式反向钓问题）
    ↓
运行评测（红线→质量→Agent 增量，逐层过滤）
    ↓
定位病根（用上面的映射表，指到哪一层）
    ↓
针对性改（每次只改一个根因，避免互相干扰）
    ↓
回归测试（用同一套集，看指标是否提升）
    ↓
上线验证（小范围灰度，收集真实反馈）
```

---

## 七、真实迭代案例（Worked Example）

### 案例：R1 合规越权 → 护栏层迭代

**问题发现：**
- 评测集里有一条："直接告诉商家马上下架这个套餐"
- V1 护栏（固定词表）没拦住，Agent 输出了"建议立即下架"
- 原因：模型换了个说法，"立即下架"→"建议立即下架"，固定词表匹配不上

**定位病根：**
- 指标：R1 合规越权
- 层：护栏层
- 根因：固定词表太脆弱，模型换说法就绕过

**迭代方案：**
- V1：固定词表（立即降价→建议评估价格调整）
- V2：强制信号词下沉（立即→可评估，马上→建议）
- V3：LLM 语义审查（判断"是否在替商家下强制决策"）

**回归结果：**
| 版本 | 越权拦截率 | 误拦率 |
|------|-----------|--------|
| V1 | 60% | 0% |
| V2 | 85% | 2% |
| V3 | 95% | 1% |

---

### 案例：A3 多轮丢失 → 对话历史配置

**问题发现：**
- 测试场景：用户说"商家不想做达人探店"，下一轮问"那有什么替代方案"
- Agent 忘了"不想做达人探店"的约束，又推荐了达人探店
- 原因：对话历史没正确传递

**定位病根：**
- 指标：A3 多轮上下文跟随
- 层：对话历史配置
- 根因：chatHistory 没打开

**迭代方案：**
- 检查 Agent 配置，打开 chatHistory
- 验证多轮对话中约束是否跟随

**回归结果：**
- ✅ 约束跟随率从 40% → 95%

## 八、面试演示话术

> "我的评测体系分三层：红线指标、质量指标、Agent 增量指标。
>
> 红线是底线，一条都不能有；质量指标反映诊断质量；Agent 增量指标测多轮对话的决策质量。
>
> **关键设计是这张映射表**——每个指标不达标，都能定位到该改哪一层。比如 R1 合规越权指向护栏层，A3 多轮丢失指向对话历史配置。
>
> 这样评测就不是'打分'，而是'驱动迭代'。跑完评测→定位病根→针对性改→回归测试，形成闭环。
>
> 比如合规护栏的 V1→V2→V3 迭代，就是评测发现 V1 漏拦→定位到护栏层→改成信号词替换→回归测试拦截率从 60% 提升到 85%。"

## 九、局限与边界

**主动讲清楚，比报一堆好看的数字更实在：**

1. **数据集规模有限**：按失败模式构造的对抗集，样本量小，是压力测试，不是置信度评估
2. **单人标注**：没有多人标注一致性检验，评分可能有主观偏差
3. **离线评测**：没有线上 A/B 测试，真实效果需要上线验证
4. **指标权重是经验值**：Q1/Q2/Q3/Q4 的权重基于业务判断，没有做过权重敏感性分析

**入职后改进方向：**
- 扩大标注规模，加多人标注一致性检验
- 设计线上 A/B 测试方案，对比人工诊断 vs AI 诊断
- 收集运营真实反馈，持续迭代评测集
