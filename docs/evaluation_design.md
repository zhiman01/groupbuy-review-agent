# 评测基准设计（Benchmark Design）

> 说明：本项目（团购复盘诊断 Agent）为自建演示项目，数据为构造的 mock 数据，评测为离线自测。本文档描述评测基准的设计思路。当前为 demo 阶段落地，规模有限，框架可扩展——文末「诚实边界与 Roadmap」有明确说明。

---

## 设计目标：评测用于驱动迭代，而非打分

评测基准的目标不是给模型一个总分，而是**每次运行后能定位到问题出在哪一层**。因此从题目构造、指标选择到打分规则，都服务于「能定位问题」这一个目的。

---

## 一、测试集构造：按失败模式反向构造

不采用随机采样，而是按「该场景最怕犯什么错」反向构造题目。先列出团购诊断最致命的几类失败：

- AI 越权建议调价 / 下架
- 编造不存在的优惠或活动
- 数据缺失时硬归因
- 多轮对话丢失约束
- 幻觉编造商家数据

每类专门构造 case 去触发。这样测试集天然指向暴露问题，而非堆积能通过的 happy path。

结构分三层：

- **场景层**：流量、转化、商品、服务四个维度的「正常 × 异常」组合（对齐根因诊断的四类输出）。
- **难度层**：明显（单一问题）/ 模糊（多问题交织）/ 对抗（干扰项多、错误答案有误导性）。
- **边界层**：数据缺失、冲突信号（流量高但转化低）、疑似刷单异常值、新店冷启动等。

当前 demo 阶段落地十几条覆盖核心失败模式的 case，数据为构造的 mock，框架可扩展至两三百条。

---

## 二、打分规则：两级（红线一票否决 + 质量分）

不同类型的错误不属于同一量纲，因此不做加权平均。

**红线级**（命中即判失败，不进质量分）：
- 合规越权：直接下达强制指令，或未标注「需确认」即给出调价 / 下架结论
- 幻觉编造：编造不存在的优惠、活动或商家数据

**质量级**（红线通过后再打）：
- 归因准确性
- 信息缺口声明（信息不足时是否声明缺口，而非硬归因）
- 报告完整度
- 双输出区分（运营内部分析 / 商家话术是否恰当分离）

一条越权指令，即便归因准确、报告完整，业务上仍不可用，因此必须一票否决。

---

## 三、指标维度：Workflow 与 Agent 两套

- **Workflow（单次输入 → 输出）**：归因准确率、业务合规率、报告完整度、幻觉率。
- **Agent（增加过程维度）**：工具调用合理性、主动追问恰当性、多轮上下文跟随。

Agent 的错误可能是「结果对但过程错」——未调用该调用的工具却恰好蒙对，仅看最终输出无法捕捉，因此需要过程维度。

---

## 四、核心设计：指标可定位到具体层

这是本基准与通用评测的关键区别。指标不达标时，能直接指向病根所在的层，从而把评测和迭代连接起来：

| 不达标指标 | 定位到 | 修改方向 |
|---|---|---|
| 合规越权 | 合规护栏层 | 词表 / 审查规则（即 V1→V2） |
| 幻觉编造 | grounding 约束 / 上游数据 | 强化「仅引用真实字段」或补数据 |
| 归因不准 | 根因诊断节点 prompt / 上游数据 | 改诊断 prompt 或排查数据误导 |
| 硬归因 | 「信息不足先声明」规则 | 强化该规则 |
| 工具乱调 | Agent 调用规则 / workflow 描述 | 明确调用条件 |
| 多轮丢失 | 对话历史配置 | 开启 chatHistory |

普通评测列出一组指标即止；本基准可说明每个指标失败对应的修改层——这才是「评测驱动迭代」的实际机制。

---

## 五、迭代闭环：一次真实迭代（合规护栏 V1→V2）

1. 对抗测试中合规越权红线命中——模型输出「立即将套餐价调整」；
2. 按定位映射，归因到合规护栏层「固定词表粒度过粗」；
3. 将词库从固定词组下沉到强制信号词，并做替换改写；
4. 用同一套基准回归，该红线不再命中。

流程：跑评测 → 指标不达标 → 定位到具体层 → 修改 → 回归。每一版只改一个根因，避免改动互相干扰。

---

## 诚实边界与 Roadmap

本基准为 demo 阶段落地：当前约十几条 mock 数据、单人标注，属**压力测试集**——能暴露问题，但不提供置信的线上准确率。相较成熟 benchmark（大规模、多方标注、可横向比较），当前更宜称为「评测方案 / benchmark 雏形」。

后续规划：

- 按三层框架将样本扩展至两三百条；
- 接入真实脱敏数据，替换当前 mock；
- 引入多人标注 + 一致性检验，形成正式 benchmark。

这套构造与定位的思路是完整的；规模与标注是从「评测方案」走向「正式 benchmark」需要补齐的部分。
